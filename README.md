# Scheduler

Трекер рабочих задач для медицинского персонала. Rails 8 API с поддержкой разовых и повторяющихся задач, тегами и swagger-документацией.

**Стек:** Ruby 3.4, Rails 8.1, PostgreSQL 16, Docker

---

## Запуск

### Требования

- Docker Desktop
- GNU Make

### Первый запуск

```bash
make setup
```

Команда соберет образ, создаст БД, выполнит миграции и заполнит системные теги.

### Последующие запуски

```bash
make up    # запустить
make down  # остановить
make logs  # логи
```

### Тесты

```bash
make test
```

### Обновить swagger-документацию

```bash
make swagger
```

---

API доступно на `http://localhost:3000`

Swagger UI: `http://localhost:3000/api-docs`

## Примеры запросов

### Создание разовой задачи

```bash
curl -X POST http://localhost:3000/api/v1/tasks \
  -H "Content-Type: application/json" \
  -d '{
    "task": {
      "title": "Связаться с пациентом Ивановым",
      "description": "Уточнить результаты анализов",
      "due_date": "2026-06-15",
      "recurring": false
    }
  }'
```

### Создание повторяющейся задачи (ежедневно)

```bash
curl -X POST http://localhost:3000/api/v1/tasks \
  -H "Content-Type: application/json" \
  -d '{
    "task": {
      "title": "Утренний обход пациентов",
      "recurring": true,
      "starts_on": "2026-06-01",
      "ends_on": "2026-12-31",
      "recurrence_rule": {
        "rule_type": "daily",
        "interval": 1
      }
    }
  }'
```

### Создание задачи на четные дни (бессрочная)

```bash
curl -X POST http://localhost:3000/api/v1/tasks \
  -H "Content-Type: application/json" \
  -d '{
    "task": {
      "title": "Формирование отчетности",
      "recurring": true,
      "starts_on": "2026-06-01",
      "recurrence_rule": {
        "rule_type": "even_odd",
        "even_odd": "even"
      }
    }
  }'
```

### Получение задач за период с фильтрацией

```bash
# Все задачи за июнь 2026
curl "http://localhost:3000/api/v1/tasks?date_from=2026-06-01&date_to=2026-06-30"

# Только pending-задачи
curl "http://localhost:3000/api/v1/tasks?date_from=2026-06-01&date_to=2026-06-30&status[]=pending"

# Задачи с конкретными тегами (AND-логика)
curl "http://localhost:3000/api/v1/tasks?date_from=2026-06-01&date_to=2026-06-30&tag_ids[]=1&tag_ids[]=2"
```

### Отметить конкретный день повторяющейся задачи выполненным

```bash
curl -X PATCH http://localhost:3000/api/v1/tasks/1/occurrences/2026-06-10 \
  -H "Content-Type: application/json" \
  -d '{
    "occurrence": {
      "status": "completed"
    }
  }'
```

### Переопределить экземпляр (оторвать от шаблона)

```bash
curl -X PATCH http://localhost:3000/api/v1/tasks/1/occurrences/2026-06-12 \
  -H "Content-Type: application/json" \
  -d '{
    "occurrence": {
      "title": "Обход перенесен на 14:00",
      "description": "Из-за совещания"
    }
  }'
```

### Отменить конкретный день

```bash
curl -X DELETE http://localhost:3000/api/v1/tasks/1/occurrences/2026-06-15
```

### Привязать тег к задаче

```bash
curl -X POST http://localhost:3000/api/v1/tasks/1/tags \
  -H "Content-Type: application/json" \
  -d '{ "tag_id": 1 }'
```

Полная документация доступна в Swagger UI: `http://localhost:3000/api-docs`

## Архитектурные решения

### Сервисный слой

Контроллеры тонкие, вся бизнес-логика вынесена в сервисы (`app/services/`). Сервисы возвращают `Dry::Monads::Result` (`Success`/`Failure`). Валидация входных данных через `Dry::Validation` контракты (`app/contracts/`), отдельные для создания (`CreateTaskContract`) и обновления (`UpdateTaskContract`).

### Решение проблемы бесконечности: calendar_dates

Повторяющиеся задачи не создают записи в БД заранее. Вместо этого используется справочная таблица `calendar_dates` (~3 650 строк, предзаполнена на 2025-2035), содержащая метаданные каждого дня (день месяца, день недели, четность). Вхождения вычисляются через SQL JOIN `tasks -> recurrence_rules -> calendar_dates` для запрошенного диапазона дат. Это решает проблему бесконечности: бессрочная ежедневная задача не создает миллионов записей.

**Почему не генерация на лету:** SQL JOIN по готовой таблице с индексами эффективнее, чем `generate_series` с вычислением атрибутов каждой даты при каждом запросе. Таблица небольшая (~3 650 строк) и легко расширяется.

### Состояние экземпляра: sparse task_occurrences

Таблица `task_occurrences` использует ленивый подход: запись создается только при взаимодействии пользователя с конкретным днем (отметил выполненным, изменил, отменил). При выборке: если запись есть, берется ее status/title/description; если нет, используются значения из шаблона задачи со статусом `pending`.

Это позволяет:
- Экономить место: для задачи на 365 дней в БД может быть 0 записей, если никто не взаимодействовал
- Переопределять отдельные поля экземпляра ("оторвать" от шаблона)
- Отменять конкретные дни без влияния на остальные

### Список задач: UNION ALL с SQL-пагинацией

Список задач (`GET /api/v1/tasks`) объединяет разовые задачи и вычисленные вхождения повторяющихся через `UNION ALL` в одном SQL-запросе. Сортировка (`ORDER BY`) и пагинация (`LIMIT/OFFSET`) выполняются на уровне БД, а не в памяти приложения.

### Ограничение диапазона дат

Для защиты от перегрузки запрос `GET /api/v1/tasks` ограничен диапазоном 90 дней. Если `date_from`/`date_to` не указаны, используется период "сегодня + 90 дней". Если клиент запрашивает больший диапазон, `date_to` обрезается.

### Системные теги

Три тега ("отчетность", "операции", "звонок") создаются через seeds и помечены флагом `system: true`. API запрещает их редактирование и удаление. Пользовательские теги можно создавать, изменять и удалять свободно.

## Допущения

1. **Авторизация отсутствует.** На данном этапе API открыто, нет разделения на роли (врач/администратор). В продакшене потребуется аутентификация (JWT/devise) и авторизация (Pundit или подобные).

2. **Горизонт планирования: 2025-2035.** Таблица `calendar_dates` предзаполнена на 10 лет. Для расширения достаточно выполнить миграцию с `INSERT` дополнительных дат.

3. **Monthly day_of_month > 28.** Если задача повторяется на 31-е число, в месяцах с меньшим количеством дней (февраль, апрель и т.д.) вхождение просто не создается. Как вариант - сделать перенос на последний день месяца.

4. **Часовые пояса не учитываются.** Задачи оперируют датами (`Date`), не моментами времени (`DateTime`). Для MVP этого достаточно; при необходимости можно добавить поле времени и timezone.

5. **Статус recurring-задачи** это статус по умолчанию для новых вхождений. Изменение статуса шаблона не затрагивает уже созданные occurrence-записи.

6. **Soft delete не реализован.** Удаление задач физическое (`DELETE`). В продакшене скорее всего потребуется soft delete и логи изменений (PaperTrial к примеру).

7. **Валидация occurrence-дат.** При создании/отмене occurrence проверяется, что дата действительно попадает в правило повторения задачи. Нельзя отметить выполнение на дату, когда задача не должна была произойти.

## Известные ограничения

- Нет массовых операций над серией ("изменить все будущие", "удалить серию").
- Нет полнотекстового поиска по title/description.

## Возможные улучшения

- Аутентификация (JWT/devise) и авторизация по ролям (Pundit, CanCan)
- Массовые операции над серией задач ("изменить все будущие", "удалить серию")
- Дополнительные типы повторений (например, еженедельные по дням недели)
- Soft delete и аудит-лог изменений
- Привязка задач к пользователям и пациентам
- Уведомления и напоминания о предстоящих задачах
- Полнотекстовый поиск по title/description
